# 案例Schema定义

本文档定义了知识库中案例的JSON格式规范。

## 统一格式（req和general）

`req`和`general`文件夹的案例使用相同的格式，区别仅在于领域不同。有无上下文体现在`input`字段是句子还是段落。

```json
{
  "case_id": "case_001",
  "input": "原始输入（句子或段落）",
  "ambiguity_type": "歧义类型",
  "analysis": "歧义分析过程（文本描述）",
  "resolved": "消歧后的句子"
}
```

### 字段说明

- `case_id`: 案例唯一标识
- `input`: 原始输入
  - **句子**：无上下文的单个句子
  - **段落**：包含上下文的段落（req_standard必须使用段落）
- `ambiguity_type`: 歧义类型（如"多义词歧义"、"指代歧义"、"结构歧义"等）
- `analysis`: 歧义分析过程，文本描述，包含：
  - 识别的歧义元素
  - 可能的解读
  - 推理过程
  - 使用的规则和知识
- `resolved`: 消歧后的句子

## req_standard格式（case_reasoner格式）

`req_standard`文件夹的案例使用case_reasoner格式，必须有上下文，`input`字段必须是包含上下文的段落。

```json
{
  "case_id": "reqs_001",
  "input": "包含上下文和歧义句的段落文本...",
  "category": "词汇/语法/指代/分词",
  "ambiguity_type": "歧义类型",
  "contexts": [
    {
      "text": "上下文信息",
      "score": 0.85
    }
  ],
  "reasoning_chain": "推理链文本描述",
  "entailment_tree": {
    "type": "conclusion",
    "content": "歧义句的多种解读",
    "children": [...]
  },
  "interpretations": [
    {
      "text": "解读1",
      "confidence": 0.75
    }
  ]
}
```

### 字段说明

- `input`: 包含上下文和歧义句的完整段落
- `category`: 歧义类别
- `ambiguity_type`: 具体歧义类型
- `contexts`: 上下文列表，每个上下文包含text和score
- `reasoning_chain`: 推理链文本描述
- `entailment_tree`: 蕴涵树结构（树形JSON）
- `interpretations`: 解读列表，每个解读包含text和confidence

## 格式示例

### req文件夹（无上下文，单个句子）

```json
{
  "case_id": "req_001",
  "input": "系统需要实现用户接口，该接口应支持多种认证方式。",
  "ambiguity_type": "多义词歧义+指代歧义",
  "analysis": "识别到'接口'一词出现两次。第一个'接口'存在词汇歧义：可能指用户界面(UI)或应用程序接口(API)。第二个'接口'存在指代歧义：可能指代第一个'接口'的任意一种含义。\n\n推理过程：\n1. 根据'用户接口'的常见用法，在需求文档中通常指用户界面(UI)\n2. 根据'支持多种认证方式'的上下文，更符合UI的功能特征\n3. 应用最近指代原则，第二个'接口'指代第一个'接口'(UI)\n\n使用的规则：LEX-001（领域上下文优先）、REF-001（最近指代原则）\n使用的知识：TERM-001（接口定义）",
  "resolved": "系统需要实现用户界面，该用户界面应支持多种认证方式。"
}
```

### general文件夹（无上下文，单个句子）

```json
{
  "case_id": "general_001",
  "input": "咬死了猎人的狗",
  "ambiguity_type": "结构歧义",
  "analysis": "识别到语法结构歧义。存在两种可能的句法结构：\n1. '咬死了(猎人的狗)' - 某物咬死了猎人的狗\n2. '(咬死了猎人)的狗' - 狗咬死了猎人\n\n推理过程：\n1. 分析'咬死'的语义特征，其主语必须是有生命实体\n2. '狗'是有生命实体，可以作为主语\n3. '猎人'也是有生命实体，可以作为宾语\n4. 根据语义合理性，第二种解读更符合常见场景\n\n使用的规则：SYN-001（动宾关系判断）、SYN-002（偏正结构识别）",
  "resolved": "狗咬死了猎人"
}
```

### req_standard文件夹（有上下文，段落）

```json
{
  "case_id": "reqs_001",
  "input": "在用户认证模块的设计中，系统需要实现用户接口。该接口应支持多种认证方式，包括用户名密码、手机验证码和第三方登录。",
  "ambiguity_type": "多义词歧义+指代歧义",
  "analysis": "识别到'接口'一词出现两次。第一个'接口'存在词汇歧义：可能指用户界面(UI)或应用程序接口(API)。第二个'接口'存在指代歧义。\n\n上下文分析：\n- 上下文提到'用户认证模块的设计'，这是需求文档的典型场景\n- '支持多种认证方式，包括用户名密码、手机验证码和第三方登录'，这些功能更符合用户界面的特征\n\n推理过程：\n1. 根据上下文'用户认证模块的设计'，判断为需求文档场景\n2. 根据'支持多种认证方式'的详细描述，判断为UI接口\n3. 应用最近指代原则，第二个'接口'指代第一个'接口'(UI)\n\n使用的规则：LEX-001（领域上下文优先）、REF-001（最近指代原则）\n使用的知识：TERM-001（接口定义）、CTX-REQ-001（需求文档中用户接口通常指UI）",
  "resolved": "在用户认证模块的设计中，系统需要实现用户界面。该用户界面应支持多种认证方式，包括用户名密码、手机验证码和第三方登录。"
}
```

## 文件组织

- `req/`: 需求工程领域案例（无上下文，input是句子）
- `req/with_context/`: 需求工程领域案例（有上下文，input是段落）
- `req_standard/`: 需求工程领域标准案例（必须有上下文，input是段落）
- `general/`: 普通领域案例（无上下文，input是句子）
- `general/with_context/`: 普通领域案例（有上下文，input是段落）
